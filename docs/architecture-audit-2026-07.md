# Аудит архитектуры, парсера и tools (2026-07)

**Дата:** 2026-07-10 · **Формат индекса на момент аудита:** `INDEXER_VERSION` 14
**Область:** база данных (схема), парсер выгрузки 1С, MCP-tools — с точки зрения архитектора (цельность на долгий срок) и агента (потребителя MCP).

## 1. Резюме

Проект в **хорошем инженерном состоянии**: трёхслойная модель метаданных выдержана, дисциплина `NO_DB_MIGRATIONS` / `INDEXER_VERSION` соблюдается, парсер опирается на реальные выгрузки и покрыт тестами (26 файлов, ~3160 строк), сборка атомарна и устойчива к особенностям Windows. Форменная EAV-модель (v12–14) — концептуально правильный шаг: она убрала «россыпь» колонок и JSON-блобов.

Ключевой вывод: **архитектура и парсер зрелые; основной запас улучшений — в экономии токенов на стороне tools и в объёме EAV.** Три момента заслуживают внимания в порядке приоритета:

1. **`get_object_structure` не имеет режима «кратко»/лимита** — на широких объектах (Номенклатура Планеты — 155 реквизитов) отдаёт всё одним ответом (~5–6 тыс. токенов). Это единственная крупная «дыра» экономии среди основных tools.
2. **Drill-down по формам (`get_form_item` / `get_form_attribute`) возвращает EAV без курирования** — все свойства подряд, включая структурный шум (`*.AdditionSource.Type`, `ToolTip.item.lang`, дефолтные `Period.*`). Сигнал тонет.
3. **EAV захватывает 100% поддерева XML** — `form_entity_properties` = 2.16 млн строк в Планете (67% всех строк схемы), из них заметная доля — локализационный и структурный шум, который не нужен ни в обзоре, ни в drill-down.

Ни одна из проблем не является архитектурным дефектом — это настройка экономии на уже правильном фундаменте.

## 3. Архитектура базы данных

### 3.1 Сильные стороны

- **Трёхслойная модель выдержана** (`metadata_objects` / `metadata_type_slots` / `metadata_relations`), единый каталог (`CatalogRef.X` → объект напрямую, без обёрток), доменные таблицы (`fo_content_ref`, `scheduled_jobs`, `role_*`) не дублируются в общем графе. Это именно та цельность, к которой стремится архитектор.
- **EAV форм (`form_entity_properties`)** — правильная замена «колонки/JSON»: одна таблица свойств, типы — только в слотах, дочерние сущности остаются сущностями (колонки ValueTable, дерево `form_items`). Принципы P1–P8 из [`form-entity-model.md`](form-entity-model.md) реализованы последовательно.
- **Синтетические `TypeDescriptor`** для примитивов с UNIQUE-дедупликацией и кэшем резолвера — корректно и без дублей (баг 2026-06-14 закрыт).
- **Атомарная сборка**: `.db.tmp` + sidecar `.building` + `os.replace`, `journal_mode=DELETE` для temp, MCP не использует базу под маркером. Надёжно на Windows.
- **Индексация** адекватна нагрузке: FTS5 external-content (`content='modules'` — код не дублируется), FK-индексы на слотах/грантах/связях.

### 3.2 Замечания (взгляд архитектора)

- **A-1 · EAV захватывает весь поддеревом XML, без «денай-листа».** `flatten_entity` эмитит каждый лист поддерева. Отсюда:
  - `*.item.lang` для каждой локализованной строки, кроме буквального `Title` (спец-кейс в `_extract_leaf_value` только для тега `Title`). В Планете это ≈ **106 тыс. строк** чистого шума (`ToolTip.item.lang` + `…Presentation.item.lang`), значение всегда `ru`.
  - структурные пары `*.AdditionSource.Item` / `*.AdditionSource.Type`, дефолтные `Period.startDate/endDate/variant` и т.п.
  - `form_entity_properties` — **самая большая таблица схемы по числу строк** (67% всех строк в Планете) и главный драйвер размера БД после кода и FTS.
  - Это не ошибка модели EAV, а отсутствие фильтра на входе. Небольшой «денай-лист» путей + схлопывание локализованных строк (`<Tag><item><content/><lang/></item>` → одно значение `Tag`) убрал бы ~10–15% строк и весь шум `lang`.
- **A-2 · Три полных индекса на `form_entity_properties`** (`ix_fep_entity`, `ix_fep_path`, `ix_fep_name`) поверх 2.16 млн строк. При этом `ix_fep_path`/`ix_fep_name` реально нужны лишь для узкого набора «горячих» путей (`QueryText`, `DataPath`, `Visible`, `Enabled`). **Партиальные индексы** (`WHERE property_path IN (…)` / `property_name='QueryText'`) дали бы тот же план запроса при кратно меньшем размере индекса. `ix_fep_entity` (основной drill-путь) оставить полным.
- **A-3 · `role_grants` — денормализованные qname-строки** (`target_qname` + `parent_object_qname`), 812 тыс. строк / 89 МБ в Планете. Это осознанный компромисс (ссылка по имени устойчива к adopted-объектам расширений), и summary-режим tools его компенсирует. Отмечаю как самый крупный текстовый денормализат — на будущее держать в поле зрения, не трогать сейчас.
- **A-4 · `form_conditional_appearance.xml_data` хранит сырой XML** (2.2 МБ в Планете) — сознательно отложено ([`form-entity-model.md`](form-entity-model.md) §6), противоречит P5 («no raw XML»), но только в хранилище; агенту не отдаётся. Приемлемо как временное состояние — стоит зафиксировать TODO, чтобы не забыть.
- **A-5 · Сборка — одна гигантская транзакция** (`cache_size=-256000`, `temp_store=MEMORY`, commit в конце `_insert_configuration`). Для АСБ 5.8 ГБ это 148 c и держит всё в памяти/temp. Работает, но это потолок; FTS индексируется построчно во время транзакции, а не через отложенный rebuild. Оптимизировать только если появятся выгрузки, где это станет узким местом.

## 4. Парсер (`shared/xml_parser/`)

### 4.1 Сильные стороны

- Per-object dispatch по whitelist, постадийный тайминг (`stage_seconds` + `_accumulate`), два формата выгрузки (2.20 `ChildObjects` и классическая обёртка `Attributes`).
- Реальная устойчивость: `_winlong()` (`\\?\`) решает Windows `MAX_PATH` — найдено и починено на живой выгрузке АСБ.
- BSL-границы: многострочные сигнатуры, `&`-директивы, аннотации расширений (`&Вместо/&После/…`), trailing `// Имя()` после `КонецФункции` (фикс 2026-07-10). Индекс процедур точный, срез кода — по `start_line/end_line`.
- Опора на реальные выгрузки + бенчмарки. Дисциплина «не угадывать» соблюдается.

### 4.2 Замечания

- **P-1 · Over-capture во flattener (см. A-1).** Правится на уровне парсера: положительный/отрицательный список путей и схлопывание локализованных строк. Даёт эффект и по хранилищу, и по ответам агенту. Требует bump `INDEXER_VERSION` (пересборка).
- **P-2 · `_parse_form` глушит любые исключения `print`-ом и возвращает `None`.** Битая форма молча выпадает из индекса; сообщение уходит в stdout, а не в лог сборки/статистику. На больших реальных выгрузках это может скрыть потерю данных. Рекомендуется считать и показывать счётчик пропущенных форм в `progress_callback`/статистике.
- **P-3 · Резолюция типов оставляет «пустые» типы у части реквизитов форм.** В `get_form_structure` видно `Организации:` / `ВидыОтчетов:` без типа (реквизит-коллекция/необёрнутый тип, не покрытый `metadata_type_resolver`). Косметика, но агенту неинформативно — стоит либо резолвить такие обёртки, либо явно писать `(тип не определён)`.
- **P-4 · Всё дерево объектов держится в памяти** до вставки (не потоково). Для 11–19 тыс. объектов работает, но это архитектурный потолок; трогать только по метрикам.
- **P-5 · `search_code` LIKE-ветка сканирует `modules.code` (851 МБ)** при спецсимволах/фильтрах. Ограничено `MAX_MODULES_SEARCH_CODE=100`, для редких запросов — полный проход. Известный компромисс, оставить как есть до реальных жалоб.

## 5. MCP-tools

### 5.1 Сильные стороны

- **Покрытие полное и слоистое:** discovery (`active_databases`, `list_objects`, `find_object`, `find_attribute`, `find_form`, `find_role`) → структура (`get_object_structure`, `get_form_structure`) → drill-down (`get_form_attribute`, `get_form_item`, `get_module_code/procedures/procedure_code`) → обратные связи (`find_referencing_objects`, `find_roles_for_object`, `get_functional_options`) → права (`get_role_rights`). Приоритеты для агента задокументированы.
- **Экономия там, где это критично:**
  - `get_role_rights` **summary-режим** — эталон: `ПолныеПрава` (10 048 грантов) сворачивается в `grant_stats` + hint вместо перечисления. Проверено вживую.
  - `get_form_structure` — обзор с профилями по типу элемента, скрытие колонок Table/ValueTable, `QueryText` только подсказкой. Реально компактно (проверено на `НастраиваемыйОтчет.ФормаСписка`).
  - `search_code` — лимит модулей + лимит вхождений на модуль + сниппет-окна.
  - Единообразные сигналы усечения (`is_truncated`, `total_count`, `returned_count`).
- **Адресное извлечение кода** (процедура по границам строк, срез `modules.code`) — не возвращает модуль целиком.
- Кэш соединений SQLite с инвалидацией по `mtime`.

### 5.2 Замечания (взгляд агента / экономия)

- **T-1 · `get_object_structure` — нет режима «кратко»/лимита. (High)** На Номенклатуре Планеты — 155 реквизитов + 6 ТЧ + 16 форм в одном ответе. В отличие от `list_objects` и role-tools, здесь нет `limit`, нет фильтра по секциям, нет summary. Это главный оставшийся перерасход токенов среди основных tools.
  - Рекомендация: опциональный `sections` (`attributes|tabular_sections|forms|modules|commands`) и/или `max_attributes` с `is_truncated`; либо summary-режим (только счётчики + стандартные реквизиты) с уходом в `find_attribute` за деталью. Минимум — лимит + флаг усечения.
- **T-2 · Drill-down отдаёт EAV без курирования. (High)** `get_form_item`/`get_form_attribute` печатают все строки EAV в алфавитном порядке путей, включая шум (`SearchControlAddition.AdditionSource.Type`, `Period.*` дефолты, `RowsPicture.LoadTransparent`, `ToolTip.item.lang`). На Table «Список» — 25 строк, ~40% низкоценные. Нет приоритезации (ключевые свойства первыми) и нет подавления шума. Причём `_form_item_detail` уже вычисляет `overview_properties`, но dispatch их для самого элемента игнорирует.
  - Рекомендация: подавлять известные шумовые пути (`*.lang`, `*.AdditionSource.*`, пустые/дефолтные значения) и/или сортировать «профиль сначала, остальное потом»; опционально `verbose=false` по умолчанию (курировано) с полным дампом по запросу.
- **T-3 · Несогласованность формата ответов. (Medium)** Role-tools отдают сырой JSON, остальные — форматированный текст. Агент получает две разные формы. JSON компактен и парсится — вопрос только консистентности; зафиксировать единый контракт.
- **T-4 · `search_form_properties` умеет только `Visible`/`Enabled`. (Medium)** EAV делает обобщение до любого `property_path` тривиальным (см. [`form-entity-model.md`](form-entity-model.md) §5.3). Сейчас новая EAV недоиспользована этим tool.
- **T-5 · `search_code` всегда выполняет доп. запрос по `QueryText` в EAV**, даже когда `module_type` сузил поиск до немодульных форм; поиск по тексту запроса не ограничен лимитом модулей. Мелочь, но лишний скан на каждом вызове.
- **T-6 · Стоимость схем tools.** 18 tools, ~34 КБ схем — фиксированная цена каждого вызова агента. Описание `active_databases` перегружено ключевыми словами (11 строк). Терпимо; при желании — подрезать.
- **T-7 · `find_referencing_objects`** грузит всех referencer-ов в память и потом срезает по `max_results`. Для «популярных» объектов (Организация: тысячи слотов + гранты) память ок, вывод ограничен. Замечание на будущее, не блокер.

## 7. Вывод

С позиции архитектора долгосрочная модель **корректна и не требует переделки**: слои разделены, каталог единый, дисциплина версий и пересборки соблюдается. С позиции агента MCP **удобен и в большинстве сценариев экономен**, а лучшие практики (summary-режим ролей, профили форм) стоит распространить на два оставшихся «тяжёлых» ответа — `get_object_structure` и form-drill-down. Основной технический долг — не в структуре, а в том, что форменная EAV захватывает и отдаёт больше, чем нужно; это чинится точечно (фильтр на входе + курирование на выходе) без изменения архитектуры.
