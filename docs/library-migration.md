# Переход C-MCP на единый движок формата (`1c-metadata-schema`)

Стратегическая заметка. Фиксирует направление и ближайший шаг (СКД). Детальная
проработка схемы хранения СКД — отдельная задача, здесь только выводы и рамка.

## Цель

Единый источник знания формата 1С-XML на **чтение и запись** — библиотека
`1c-metadata-schema` (`onec_metadata_schema`). Меньше точек входа, read и write не
расходятся. C-MCP — read-потребитель, `1c-help-mcp` — write-потребитель.

## Стратегия (как переводим, не ломая текущий парсер)

- **Инкрементально, за развилкой «старый путь / библиотека».** Разбор каждого блока
  оборачивается в ветку: пока новый путь не доказан на реальных выгрузках — работает
  старый; доказали — старый убираем. Внешние объекты уже так и устроены (развилка по
  типу корня в `shared/xml_parser/core.py`).
- **Новое — сразу библиотекой** (там, где ломать нечего — нулевой риск регрессии).
  Старые whitelist-типы переводим потом, по одному, каждый за своей развилкой.
- **Не big-bang.** Переписывание всего `shared/xml_parser` одним махом против зрелого
  парсера без сверки — чистый регресс-риск. Отклонено.
- **Полная миграция остальных типов** осмысленна как часть Stage G (расширения) в
  `1c-metadata-schema`, а не как самоцель. См. `scope.md` там.

## Почему СКД — первый шаг

Идеальный первый кусок «через библиотеку»:

- **Старый парсер СКД не читает вообще** → ломать нечего, чистое добавление.
- **Запись СКД библиотека уже умеет** (`onec_metadata_schema.dcs`) → чтение в том же
  месте = сразу единый источник, без старого пути под охраной.
- Даёт реальную новую пользу на read-стороне (сейчас чистый СКД-отчёт индексируется
  тонко — вся логика в схеме, а её не видно).

## Что такое СКД-контейнер (первая разведка, реальный `РВП`)

Корень `DataCompositionSchema` (`Templates/<Схема>/Ext/Template.xml`). Ключевые области:

| Область | Пример на `РВП` | Ценность для индекса |
|---|---|---|
| `dataSet` → `query` (текст запроса) | 1 набор, **7220 симв.** запроса | **высшая** — что и откуда читает отчёт |
| `field` / `dataPath` | 92 поля / 45 путей | поля набора, их роли/типы |
| `dataSource` | 2 источника | подключение (обычно к ИБ) |
| `calculatedField` | 1 | вычисляемые поля (выражения) |
| `totalField` | 3 | итоги/ресурсы |
| `parameter` | 17 | параметры отчёта (период и т.п.) |
| `settingsVariant` → `settings` | 1 вариант | компоновка по умолчанию: `selection`/`filter`/`order`/группировки |
| `role` | 6 | роли полей (измерение/период/баланс…) |

**Первый срез (низкая цена, высокая польза):** текст запроса набора данных → в
`code_search` (FTS), как модуль. Тогда `search_code` находит отчёты по тому, какие
таблицы/поля они запрашивают. Остальное (поля, параметры, вычисляемые/итоговые,
настройки) → **новые таблицы**, требует проработки схемы.

## Важные уточнения по охвату (из реальных выгрузок)

- **СКД — не только у отчётов.** `DataCompositionSchema`-шаблоны встречаются на
  `Catalog` / `Document` / `BusinessProcess` и в `CommonTemplates` тоже (напр.
  `Расш бюдж/Catalogs/ФТ_СтруктураБДДС/Templates/ОтборСтатейБДДC`). Индексация СКД —
  общий механизм для шаблонов, а не «фича отчёта».
- **`Templates/` неоднороден:** СКД-схемы (`DataCompositionSchema`) vs табличные макеты
  (MXL, корень `document` / `SpreadsheetDocument`, напр. `ПФ_MXL_*`). Это разные
  форматы — индексировать раздельно.
- **Общий эпик для встроенных и внешних отчётов** — паритет: встроенный `Report` СКД
  тоже сейчас не индексирует.

## Открытые вопросы (нужна архитектура)

- Какие области индексируем **однозначно**, а какие пропускаем на первом этапе.
- Схема хранения: **много новых таблиц** (наборы, поля, параметры, вычисляемые/итоговые,
  настройки/варианты) + связи с `metadata_objects` и `metadata_type_slots`.
- Тексты запросов: отдельная таблица или переиспользовать `code_search`/`module_procedures`?
- Как СКД крепится к объекту-владельцу (шаблон → объект) в индексе.
- `bump-indexer-version` при изменении схемы (пересборка БД без миграций).
