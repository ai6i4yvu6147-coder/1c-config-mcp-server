# Переход C-MCP на единый движок формата (`1c-metadata-schema`)

Стратегическая заметка. Фиксирует направление и ближайший шаг (СКД). Детальная
проработка схемы хранения СКД — отдельная задача, здесь только выводы и рамка.

## Цель

Единый источник знания формата 1С-XML на **чтение и запись** — библиотека
`1c-metadata-schema` (`onec_metadata_schema`). Меньше точек входа, read и write не
расходятся. C-MCP — read-потребитель, `1c-help-mcp` — write-потребитель.

## Стратегия (как переводим, не ломая текущий парсер)

- **Инкрементально, за развилкой «старый путь / библиотека».** Разбор каждого блока
  оборачивается в ветку: пока новый путь не доказан на реальных выгрузках — работает
  старый; доказали — старый убираем. Внешние объекты уже так и устроены (развилка по
  типу корня в `shared/xml_parser/core.py`).
- **Новое — сразу библиотекой** (там, где ломать нечего — нулевой риск регрессии).
  Старые whitelist-типы переводим потом, по одному, каждый за своей развилкой.
- **Не big-bang.** Переписывание всего `shared/xml_parser` одним махом против зрелого
  парсера без сверки — чистый регресс-риск. Отклонено.
- **Полная миграция остальных типов** осмысленна как часть Stage G (расширения) в
  `1c-metadata-schema`, а не как самоцель. См. `scope.md` там.

## Прогресс (на 2026-07-18/19)

Перевод read-парсера идёт треком `library-engine-migration` ([`todo.md`](todo.md)), развилка
`_parse_object` по `LIBRARY_MIGRATED_TYPES` в `shared/xml_parser/core.py`:

- **Шаг 1 — `DataProcessor`/`Report`** (через `_adapt_object_descriptor`).
- **Шаг 2 — все объектные типы с реквизитами** (`Catalog`/`Document`/`Enum`/4 регистра/2 charts/
  `ExchangePlan`/`BusinessProcess`/`Task`): `_parse_object_via_library` стал type-aware. Находки:
  старый `_parse_standard_attributes` — мёртвый код (паритет `[]`); в библиотеку внесены два
  фикса резолвера типов (`cfg:DefinedType.X` → `object_ref`; разворот `ExtendedProperty`/
  `ExtendValue`). A/B на 15 426 объектах (5 проектов) — 0 ошибок, все дифы «новое ≥ старое»;
  приёмка на живом MCP пройдена (Catalog/Document/регистр/Enum/BusinessProcess, обратные ссылки).
- **Шаг 3 — property-only типы** (`CommonModule`/`CommonCommand`/`CommonForm`/`ScheduledJob`/
  `FunctionalOption`/`DefinedType`): отдельный ассемблер `_assemble_property_only_object` (нет
  реквизитов/секций/ТЧ; развилка модулей/форм/команд по виду объекта — паритет с legacy).
  `_adapt_property_only_properties` = общая база + мелкие свойства SJ/FO; `DefinedType.type_slots`
  из библиотечного `.Type`. `LIBRARY_MIGRATED_TYPES` = **20** — все whitelist-типы дочерних
  объектов. A/B полного объекта на 14 705 объектах — 0 ошибок, 0 fallback, 2 дифа (обрезка
  хвостового пробела в `comment`, единообразно с шагом 2).
- **Шаг 4 — `Subsystem`** (последний whitelist-тип, отдельный обход `Subsystems/`, не через
  `_parse_object`): `_parse_subsystem_via_library` за развилкой (фолбэк `_parse_subsystem_legacy`);
  обход каталога и квалифицированное имя из пути остаются file-walk. `content_refs` из
  `Content.Item[].value`, `child_subsystem_names` из `descriptor.children`. A/B на 2007 подсистемах —
  0 ошибок, 0 fallback, 1 диф (пробельный `comment`). **Дескрипторная часть миграции завершена —
  все whitelist-типы на библиотеке.**

## Граница единого движка (что мигрируем, а что нет)

Библиотека `onec_metadata_schema` моделирует три read-поверхности C-MCP:

- **Дескрипторы метаданных** (MDClasses, `parse`/`Node`) — **мигрировано** (шаги 1–4).
- **СКД / DataCompositionSchema** (`dcs`/`dcs_read`) — **мигрировано** отдельным треком
  (`dcs-schema-indexing`, `shared/xml_parser/dcs.py` читает схему библиотекой). Старый парсер
  `Templates/` не читал вовсе — чистое добавление, нулевой риск.
- **Права роли / РЛС** (`Rights.xml`, схема `8.2/roles`, `rights`/`read_rights`) —
  **мигрировано** отдельным треком (`roles-engine-migration`,
  [`roles-engine-migration.md`](roles-engine-migration.md); `shared/xml_parser/roles.py`
  читает `Rights.xml` библиотекой за развилкой с legacy-фолбэком). A/B на 3010 файлах —
  0 расхождений. `Rights.xml` — **другая схема, не MDClasses**; движок получил её read-сторону
  так же, как ДКС: раньше write-round-trip, чтобы обслужить индексацию C-MCP.

**Читаемый парсером single-engine — на этом всё.** Остальные поверхности C-MCP — **другие схемы,
которые библиотека не моделирует**, и переводить их «на библиотеку» смысла нет (выигрыш единого
движка есть только там, где на той же модели стоит и write-сторона):

- **Формы** — `Form.xml`, свой формат (logform + EAV); `shared/xml_parser/forms.py`, остаётся как есть.
- **Дескриптор роли** (`Roles/<Name>.xml`, корень `MetaDataObject/Role`) — это MDClasses, но
  тривиальный property-only тип; C-MCP читает его своим `_parse_properties` в обходе `Roles/`.
  Содержательная часть роли — `Rights.xml` — уже на движке (см. выше). Перевод самого дескриптора
  — низкоценный микрослайс, не сделан намеренно.
- **Flowchart** — `Ext/Flowchart.xml`, схема `xcf/scheme` (граф точек/переходов по uuid);
  `flowchart.py`, остаётся как есть (вызывается из обоих путей `_parse_object`).
- **Модули** — BSL-исходники, вообще не XML; `modules.py`, вне зоны XML-библиотеки.

Их миграция была бы оправдана только после того, как соответствующие схемы появятся в самой
`1c-metadata-schema` (Stage G / write-сторона) — тогда это отдельные треки, не продолжение этого прохода.
Потенциальное расширение единого движка, уже поддержанное библиотекой, но пока не задействованное
на чтении: **MXL-макеты** (`spreadsheet`) — отложено (см. `dcs-schema-indexing`, MXL deferred).


## Почему СКД — первый шаг

Идеальный первый кусок «через библиотеку»:

- **Старый парсер СКД не читает вообще** → ломать нечего, чистое добавление.
- **Запись СКД библиотека уже умеет** (`onec_metadata_schema.dcs`) → чтение в том же
  месте = сразу единый источник, без старого пути под охраной.
- Даёт реальную новую пользу на read-стороне (сейчас чистый СКД-отчёт индексируется
  тонко — вся логика в схеме, а её не видно).

## Что такое СКД-контейнер (первая разведка, реальный `РВП`)

Корень `DataCompositionSchema` (`Templates/<Схема>/Ext/Template.xml`). Ключевые области:

| Область | Пример на `РВП` | Ценность для индекса |
|---|---|---|
| `dataSet` → `query` (текст запроса) | 1 набор, **7220 симв.** запроса | **высшая** — что и откуда читает отчёт |
| `field` / `dataPath` | 92 поля / 45 путей | поля набора, их роли/типы |
| `dataSource` | 2 источника | подключение (обычно к ИБ) |
| `calculatedField` | 1 | вычисляемые поля (выражения) |
| `totalField` | 3 | итоги/ресурсы |
| `parameter` | 17 | параметры отчёта (период и т.п.) |
| `settingsVariant` → `settings` | 1 вариант | компоновка по умолчанию: `selection`/`filter`/`order`/группировки |
| `role` | 6 | роли полей (измерение/период/баланс…) |

**Первый срез (низкая цена, высокая польза):** текст запроса набора данных → в
`code_search` (FTS), как модуль. Тогда `search_code` находит отчёты по тому, какие
таблицы/поля они запрашивают. Остальное (поля, параметры, вычисляемые/итоговые,
настройки) → **новые таблицы**, требует проработки схемы.

## Важные уточнения по охвату (из реальных выгрузок)

- **СКД — не только у отчётов.** `DataCompositionSchema`-шаблоны встречаются на
  `Catalog` / `Document` / `BusinessProcess` и в `CommonTemplates` тоже (напр.
  `Расш бюдж/Catalogs/ФТ_СтруктураБДДС/Templates/ОтборСтатейБДДC`). Индексация СКД —
  общий механизм для шаблонов, а не «фича отчёта».
- **`Templates/` неоднороден:** СКД-схемы (`DataCompositionSchema`) vs табличные макеты
  (MXL, корень `document` / `SpreadsheetDocument`, напр. `ПФ_MXL_*`). Это разные
  форматы — индексировать раздельно.
- **Общий эпик для встроенных и внешних отчётов** — паритет: встроенный `Report` СКД
  тоже сейчас не индексирует.

## Открытые вопросы (нужна архитектура)

- Какие области индексируем **однозначно**, а какие пропускаем на первом этапе.
- Схема хранения: **много новых таблиц** (наборы, поля, параметры, вычисляемые/итоговые,
  настройки/варианты) + связи с `metadata_objects` и `metadata_type_slots`.
- Тексты запросов: отдельная таблица или переиспользовать `code_search`/`module_procedures`?
- Как СКД крепится к объекту-владельцу (шаблон → объект) в индексе.
- `bump-indexer-version` при изменении схемы (пересборка БД без миграций).
