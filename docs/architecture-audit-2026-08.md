## 1. Резюме

Фундамент, описанный в аудите 2026-07, подтверждается: трёхслойная модель, EAV форм, атомарная сборка, дисциплина `INDEXER_VERSION` — здоровы. Новый слой проблем обнаружился ровно там, куда прошлый аудит не смотрел:

1. **Полностью отсутствуют FK-индексы по `form_id`** (5 таблиц). Замерено: `find_form` без фильтров — экстраполяция **~817 c**, после индексов — **0.6 мс**. Цена исправления: 0.3 c сборки и +7 МБ на базу 3.3 ГБ.
2. **Схема FTS5 объявлена с колонкой, которой нет в content-таблице** (`object_name` ∉ `modules`) → `rebuild`/`snippet()`/`highlight()` физически невозможны (в т.ч. рекомендация A-5 прошлого аудита **неисполнима**), а служебные колонки участвуют в `MATCH` и дают до **100% ложных попаданий**, молча съедая лимит выдачи.
3. **Разрешение объекта по точному имени берёт произвольный объект** при совпадении имён у разных видов метаданных — в ЕРП это **1 181 имя** (5.3% каталога).
4. **BSL-парсер теряет процедуры**, у которых в строке объявления есть хвостовой `//`-комментарий — **347 из 350** случаев в общих модулях ЕРП.

Все четыре — «тихие»: ошибок не возникает, ответ выглядит валидным.

## 3. Парсинг

### 3.1 · P-6 · Теряются процедуры с хвостовым комментарием в строке объявления — **High**

`_parse_module_procedures` ([`admin_tool/db_manager/bsl.py`](../admin_tool/db_manager/bsl.py)) требует конца строки сразу после `)` / `Экспорт`:

```python
r'^\s*(Процедура|Функция)\s+([А-Яа-яA-Za-z0-9_]+)\s*\((.*?)\)\s*(Экспорт)?\s*$'
```

Фолбэк на многострочную сигнатуру (`start_only_pattern`) срабатывает только при `')' not in lines[i]`, поэтому однострочное объявление с комментарием не подхватывает **никто** — процедура выпадает из индекса целиком.

**Замер по 4 589 общим модулям ЕРП:**

```
объявлений с хвостовым //  : 350
из них потеряно            : 347   (99%)
промах по всем объявлениям : 511 из 106 941 (0.48%)
```

Реальные примеры из корпуса:
- `Функция ПолучитьТаймаут(Знач Секунды = 3600) Экспорт // 1 час по умолчанию`
- `Процедура Проверить(Парам, Ещё) Экспорт // УТ:581 — ...`
- `Функция ЭтоРабочийДень() // берётся из производственного календаря`

**Последствия:** процедуры нет в `get_module_procedures`; `get_procedure_code` её не достаёт; `search_code` показывает попадания внутри неё как `<тело модуля>`. Агент делает вывод «такой функции не существует».

**Правка:** дописать `(?:\s*//.*)?` перед `$` — ровно тем же приёмом, что уже применён к `end_pattern` (фикс 2026-07-10). Требует bump `INDEXER_VERSION`.

### 3.2 · P-7 · Каждый дескриптор разбирается дважды, и вторая половина невидима в профиле — **Medium**

В [`shared/xml_parser/core.py`](../shared/xml_parser/core.py) (`_parse_object` и `_assemble_property_only_object`):

```python
node = onec_metadata_schema.parse(xml_file)      # разбор №1 (движок)
...
root = ET.parse(_winlong(xml_file)).getroot()    # разбор №2 — только ради команд
with self._accumulate('commands'):
    commands = self._parse_object_commands(root, ...)
```

**Замер на 450 дескрипторах (28 МБ, Documents/Catalogs/InformationRegisters ЕРП):** движок 1.50 c, повторный `ET.parse` +0.54 c = **+36%**.

Неочевидная часть: `ET.parse` стоит **вне** `_accumulate`, как и сам `onec_metadata_schema.parse`. Отсюда расхождение «сумма стадий 116 c против 146 c общего парсинга» (§ 2). **Профилировка, на которую проект опирается при принятии решений, systematically недосчитывает крупнейшую неоптимальность парсера.**

**Правка:** брать команды из уже разобранного `descriptor` (дети с `tag == 'Command'`) — второй проход не нужен. `INDEXER_VERSION` не поднимается при байт-паритете; верифицировать A/B по образцу `library-engine-migration`.

### 3.3 · P-8 · Формы — 58% времени парсинга; единственный реальный кандидат на параллелизм — **Medium**

84.7 c из 146 c. Формы читаются пофайлово, полностью независимы, тяжёлая часть — в C (`read_form`). Это тот случай, где `ProcessPoolExecutor` по каталогам объектов даёт близкий к линейному выигрыш и **заодно снимает потолок по памяти** (§ 3.4).

### 3.4 · P-4 (уточнение прошлого аудита) · Всё дерево объектов в памяти — теперь есть цифра

**≥ 3.8 ГБ RSS** на ЕРП, поверх этого `cache_size=-256000` (256 МБ) у SQLite. На 16-ГБ машине с открытой 1С это близко к краю; на конфигурации вдвое крупнее ЕРП — `MemoryError`. Стриминг «парсить → вставлять → отпускать» убирает потолок; сейчас блокируется тем, что `fo_resolver`/`type_name_to_id` строятся после первого прохода, — но их можно накапливать инкрементально.

### 3.5 · P-9 · Голый `except:` в чтении модуля формы — **Low**

[`shared/xml_parser/forms.py`](../shared/xml_parser/forms.py), `_parse_form_module` — `except:` возвращает `None`. В отличие от `_parse_form` (где P-2 закрыт счётчиком `skipped_forms`), потеря модуля формы нигде не считается и не всплывает в лог сборки.

## 4. Хранение данных

### 4.1 · A-6 · FTS5 объявлен с колонкой, которой нет в content-таблице — **High (скрытый структурный дефект)**

```sql
CREATE VIRTUAL TABLE code_search USING fts5(
    object_name, module_type, code,
    content='modules', content_rowid='id')
```

В `modules` **нет** колонки `object_name`. Контракт external content нарушен. Проверено на живой базе:

| операция | результат |
|---|---|
| `MATCH` с выборкой только `rowid` | **OK** ← единственное, что использует код сегодня |
| `SELECT object_name FROM code_search` | `no such column: T.object_name` |
| `snippet()` / `highlight()` | `SQL logic error` |
| `INSERT INTO code_search(code_search) VALUES('rebuild')` | `no such column: T.object_name` |
| `integrity-check`, `optimize` | OK |

**Следствия:**
- **Рекомендация A-5 прошлого аудита («отложенный `rebuild` FTS вместо построчной вставки») в текущей схеме неисполнима** — команда падает. Зафиксировать, иначе задачу возьмут и упрутся.
- Индекс невозможно пересинхронизировать или проверить иначе как полной пересборкой БД. Политика «баз без миграций» это маскирует, но `snippet()`/`highlight()` — естественный следующий шаг для `search_code` — закрыты навсегда.

### 4.2 · A-7 · Служебные колонки FTS участвуют в `MATCH` → ложные попадания съедают лимит — **High**

`object_name` и `module_type` — обычные индексируемые колонки, а `MATCH` без указания колонки ищет по всем. **Замер на ЕРП:**

| запрос | попаданий FTS | из них реально содержат слово в коде |
|---|---:|---:|
| `FormModule` | 11 880 | **0** |
| `ФормаСписка` | 2 832 | 1 496 (**47% мусора**) |

Механика ущерба неочевидна и хуже, чем «шум в выдаче». `LIMIT 100` (`MAX_MODULES_SEARCH_CODE`) применяется **до** проверки релевантности; дальше в Python `code_lower.find(query)` для ложной строки возвращает `-1` и сниппетов не даёт:

- `search_code("FormModule")` → **пустой ответ** при 11 880 «совпадений» в индексе;
- `search_code("ФормаСписка")` → около половины бюджета из 100 модулей потрачено впустую, реальные совпадения **молча обрезаны**, без `is_truncated`.

**Правка:** убрать `object_name`/`module_type` из FTS (оба и так берутся джойном) либо пометить их `UNINDEXED`. Закрывает и A-6, и A-7 одной сменой DDL. Требует bump `INDEXER_VERSION`.

### 4.3 · A-8 · `ANALYZE` не выполняется — **Medium**

В собранной базе нет `sqlite_stat1`. Планировщик работает на дефолтных эвристиках; на 3.3 ГБ это ровно тот режим, в котором он выбирает `SCAN` там, где индекс был бы лучше. Одна строка после сборки, `ANALYZE` на ЕРП занял **1.8 c**.

### 4.4 · Мелочи

- `PRAGMA synchronous=NORMAL` в конце `_insert_configuration` выполняется **после** `commit()` и прямо перед закрытием соединения — мёртвый код.
- Сервер открывает read-only соединения без `cache_size`/`mmap_size`: страничный кэш по умолчанию **2 МБ** на файл 3.3 ГБ.

## 5. Индексы — крупнейшая находка аудита

### 5.1 · A-9 · Полностью отсутствуют индексы по `form_id` — **Critical**

Ни одна из таблиц-детей формы не имеет FK-индекса:

```
form_items(form_id)                    ✗   349 180 строк
form_attributes(form_id)               ✗   137 755
form_commands(form_id)                 ✗    61 927
form_conditional_appearance(form_id)   ✗
modules(form_id)                       ✗    30 126 строк / 904 МБ кода
```

При этом соседние таблицы свои FK-индексы получили (`idx_form_events_form`, `ix_fac_form_attribute`, `idx_form_item_events_item`) — то есть это **упущение, а не осознанный компромисс**.

**Замер на ЕРП, до и после добавления пяти индексов + `ANALYZE`** (формы запросов взяты дословно из `server/tools/`):

| запрос | было | стало | ×  |
|---|---:|---:|---:|
| `find_form` без фильтров (экстраполяция на 12 695 форм) | **~817 c** | **0.6 мс** | ~10⁶ |
| `get_module_code(module_type='FormModule')` | 31.4 мс | 0.1 мс | 300× |
| `get_form_structure` → элементы формы | 32.5 мс | 0.1 мс | 300× |
| `get_form_structure` → реквизиты формы | 17.1 мс | 0.2 мс | 85× |
| `get_form_structure` → команды формы | 12.1 мс | 0.1 мс | 120× |
| `get_form_item` → дочерние элементы | 33.2 мс | 0.1 мс | 300× |

**Цена: 0.3 c на сборку и +7 МБ к базе 3.3 ГБ** (3 311 → 3 318 МБ). Лучшее соотношение эффект/затраты во всём проекте.

`get_form_structure` выполняет ~5 таких запросов за вызов → сейчас **~110 мс чистого сканирования на каждый вызов** вместо <1 мс.

### 5.2 · A-10 · `metadata_type_slots`: композитный индекс — **Low**

Запросы `find_referencing_objects` всегда идут как `WHERE object_id = ? AND source_table = '...'`, индекс только `(object_id)`. Композит `(object_id, source_table)` уберёт лишний фильтр по 423 161 строке.

### 5.3 · `search_form_properties` — умеренно

Tool сначала считает `COUNT(*)` без лимита. «Горячий» путь (`Visible`) — 35 мс; пути, которые сам же tool рекомендует в описании (`ReadOnly`, `CommandName`, `Title`) — **235–360 мс**. Не блокер, но описание инструмента активно ведёт агента на неиндексированные пути (см. A-2 прошлого аудита).

### 5.4 Проверенные и снятые подозрения

- `_resolve_config_object` (`name = ? OR synonym = ?`, `SCAN metadata_objects`) — **0.4 мс**, таблица мала. Индекс по `synonym` не нужен.
- `search_form_properties` на «холодных» путях с `LIMIT` — 1.9 мс (спасает `ix_fep_entity`). Проблема только у `COUNT(*)`.
- `_load_resolved_types_map` — корректно покрыт `ix_mts_source`.

## 6. Качество tools

### 6.1 · T-8 · Разрешение объекта по точному имени молча выбирает произвольный объект — **High (корректность)**

[`server/tools/relations.py`](../server/tools/relations.py), `_resolve_config_object`:

```sql
SELECT ... WHERE (name = ? OR synonym = ?) AND object_kind='ConfigObject' LIMIT 1
```

`LIMIT 1` без `ORDER BY` и без проверки на неоднозначность. **В ЕРП 1 181 имя принадлежит двум и более видам объектов** (5.3% каталога):

```
Взаиморасчеты   -> Document, CommonModule, AccumulationRegister, Report, Role
ОбменДанными    -> CommonModule, ExchangePlan, DataProcessor, Subsystem, Role
ОтправкаSMS     -> CommonModule, CommonForm, ScheduledJob, Role
```

`get_object_structure`, `find_referencing_objects`, `get_dcs_schema` вернут тот объект, который SQLite отдал первым. Выбор произволен и **может измениться между пересборками**. Ошибки нет, ответ выглядит валидным.

Показательно, что **ветка частичного совпадения неоднозначность обрабатывает корректно** (`status: 'ambiguous'` + список кандидатов). Механизм есть — точная ветка его обходит.

**Правка:** снять `LIMIT 1`; при >1 строке вернуть тот же `ambiguous`-контракт. Только `server/`, без пересборки.

### 6.2 · T-9 · `find_form` без обязательных фильтров — **High**

[`server/tools/forms.py`](../server/tools/forms.py) содержит три коррелированных подзапроса на каждую форму:

```sql
(SELECT COUNT(*) FROM form_attributes WHERE form_id = f.id),
(SELECT COUNT(*) FROM form_commands   WHERE form_id = f.id),
(SELECT COUNT(*) FROM form_items      WHERE form_id = f.id)
FROM forms f ... WHERE 1=1
```

По схеме `find_form` требует **только** `project_filter`; `object_name`/`form_name` опциональны. Легальный вызов `find_form(project_filter="Планета")` = 12 695 × 3 полных скана по 548 862 строкам ≈ **7 млрд обращений к строкам**. Прогон бенчмарка на этом запросе не завершился за 600 c и был снят. Для агента это выглядит как **зависший MCP-сервер**.

Индексы из A-9 убирают основную стоимость, но остаётся вторая половина: у `find_form` **нет `limit`/`is_truncated`**, хотя во всех остальных discovery-tools они есть (унификация T-1 прошлого аудита сюда не дошла).

### 6.3 · T-10 · FTS-синтаксис не экранируется → сырая ошибка SQLite наружу — **High**

Охранник в [`server/tools/code.py`](../server/tools/code.py): `special_chars = '.()[]"\''`. Не покрыты `-`, `:`, `*`, `^`, висящие `AND`/`OR`:

```
'Товар-Услуга'        -> OperationalError: no such column: Услуга
'ОбщегоНазначения:X'  -> OperationalError: no such column: ОбщегоНазначения
'Тест AND'            -> OperationalError: fts5: syntax error near ""
```

В [`server/server.py`](../server/server.py) перехватывается только `ValueError`, поэтому `sqlite3.OperationalError` уходит наружу и агент получает текст ошибки SQLite вместо осмысленного сообщения. Дефис в поисковой фразе — совершенно обычный запрос.

### 6.4 · T-11 · `search_code`: расхождение схемы и поведения, нет потолка ответа — **Medium**

Схема: `max_results` — «Максимум результатов на базу (по умолчанию 10)». Код: лимит **вхождений на один модуль**, при отдельном лимите в 100 модулей.

Реальный потолок ответа: 100 модулей × 10 сниппетов × (~400 символов сниппета + 4 строки метаданных) ≈ **сотни килобайт** в одном ответе. `handle_search_code` печатает всё без усечения и без `is_truncated` — **единственный из основных tools, куда унифицированные сигналы усечения (T-1/T-2 прошлого аудита) не дошли**.

### 6.5 · T-12 · Фильтр `module_type` выключает FTS целиком — **Medium**

`use_exact_search` истинно при **любом** заданном `object_name`/`module_type`, поэтому `search_code(query="Провести", module_type="ObjectModule")` уходит в `LIKE '%...%'` по 904 МБ кода: **232 мс** против **1.7 мс** у FTS. Фильтры прекрасно накладываются поверх FTS — джойн уже есть, достаточно дописать `AND m.module_type = ?`. Это же относится к `module_type='DcsQuery'`, который описание `get_dcs_schema` прямо рекомендует.

### 6.6 Мелкие

- `_fetch_referencing_role_grants` — `except Exception: return []` глушит любые ошибки, включая реальные.
- В JSON-схемах нет `enum` для `module_type` / `object_type` / `element_type` — допустимые значения перечислены только прозой в `description`, клиент не валидирует.
- `get_module_code` отдаёт модуль целиком без предупреждения о размере (в ЕРП есть модули на сотни КБ).

## 8. Вывод

Долгосрочная модель по-прежнему корректна — переделки не требует. Новый технический долг сосредоточен в двух местах, которые прошлый аудит не покрывал: **FK-индексы дочерних таблиц форм** и **семантика схемы FTS**. Обе проблемы «тихие» — не дают ошибок, только медленные или неполные ответы, поэтому и прожили до целевого замера на большой базе. Исправления по обеим — точечные, без изменения архитектуры.
