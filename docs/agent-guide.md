# 1C Config MCP — справка для агента

Этот сервер даёт **read-only доступ к метаданным и коду конфигурации 1С**, разобранным из
выгрузки в XML и уложенным в SQLite-индекс. Это не работающая база: здесь нет данных, нет
пользователей и сеансов, ничего нельзя изменить. Зато можно быстро и точно узнать, как
конфигурация устроена: какие объекты есть, какие у них реквизиты и типы, что написано в модулях,
как устроены формы, кто на кого ссылается, какие права раздают роли.

Записи нет ни в одном инструменте — любой вызов безопасен.

## С чего начать {#start}

1. **`active_databases` без аргументов** — всегда первый вызов. Он возвращает список проектов и
   баз (основная конфигурация + расширения). Из него берётся `project_filter`, обязательный почти
   везде, и опциональный `extension_filter`.
2. Имена передавайте **точно как в ответе**, без переименований и догадок. Не ориентируйтесь на
   имя MCP-подключения в IDE — оно может не совпадать с названием проекта.
3. Проверьте флаги базы в ответе: `is_outdated` (индекс собран старой версией индексатора) и
   `is_updating` (идёт пересборка). Такие базы **не участвуют** в остальных инструментах —
   дождитесь окончания сборки и вызовите `active_databases` снова.
4. Если работаете по задаче Хаба — один раз вызовите `set_context` с `task_id` и `session_id` из
   `work_on_task`. Дальше корреляция журнала идёт сама, повторять на каждый вызов не нужно.

Дальше — не сканируйте конфигурацию подряд. Почти всегда есть точечный инструмент под конкретную
цель; список маршрутов ниже.

## Маршруты «цель → инструмент» {#routes}

| Что нужно | Чем брать | Не тем |
|-----------|-----------|--------|
| Список объектов вида (все документы, все регламентные задания) | `list_objects(object_type=…)` | `search_code` |
| Найти объект по неточному имени или по синониму | `find_object` | `list_objects` + фильтрация глазами |
| Реквизиты, измерения, ресурсы, ТЧ, типы, формы и модули объекта | `get_object_structure` | несколько `search_code` |
| Один реквизит в большом объекте | `find_attribute` | `get_object_structure` с огромным ответом |
| **Исходящие** ссылки объекта (на что он ссылается) | `get_object_structure` → `types[]` | `search_code` по имени типа |
| **Входящие** ссылки (кто ссылается на этот справочник) | `find_referencing_objects` | `search_code` по имени объекта |
| Где в коде встречается фрагмент | `search_code` | обход модулей вручную |
| Текст конкретной процедуры | `get_procedure_code` | `get_module_code` целиком |
| Оглавление модуля перед чтением | `get_module_procedures` | `get_module_code` целиком |
| Кому и какие права даёт роль | `get_role_rights` | `search_code` по XML ролей |
| Какие роли дают права на объект | `find_roles_for_object` | перебор `get_role_rights` |
| Какая функциональная опция управляет реквизитом/элементом | `get_functional_options` | `search_code` |
| Запрос внутри схемы компоновки | `get_dcs_schema` | `get_module_code` |

Общее правило: **сначала структурный инструмент, `search_code` — в последнюю очередь.** Поиск по
тексту даёт много ложных совпадений и не знает про типы, слои и расширения; структурные
инструменты знают.

## Модули и код {#code}

- `get_module_procedures` — оглавление модуля: имена процедур/функций, экспортность, директивы
  компиляции. Дешёвый способ понять модуль перед чтением.
- `get_procedure_code` — текст одной процедуры вместе с её директивой (`&НаСервере` и т. п.).
- `get_module_code` — весь модуль; для больших общих модулей это дорого, предпочитайте два
  предыдущих.
- Модуль команды объекта: `get_module_code` с `module_type="CommandModule"` **и** `command_name`
  (имя из секции `commands` в `get_object_structure`). Для общей команды (`CommonCommand`)
  `command_name` не нужен.
- `search_code` ищет и по тексту запросов: в `QueryText` динамических списков форм
  (`match_kind='form_query'`) и в запросах наборов СКД (`module_type='DcsQuery'`). Есть лимит
  числа модулей на базу — при усечении в ответе сказано об этом, сузьте `project_filter` или
  добавьте `object_name` / `module_type`.

## Формы {#forms}

Форма разобрана в EAV-модель, поэтому работа с ней двухступенчатая: сначала обзор, затем
детализация нужного элемента.

1. `find_form` — найти форму по имени объекта и/или формы.
2. `get_form_structure` — обзор: реквизиты с `types[]`, дерево элементов, команды. Дочерние
   колонки таблиц **не разворачиваются** — вместо них подсказки (`columns: N`,
   `QueryText: present (N chars)`).
3. `get_form_attribute(attribute_name[, column_name])` — детали реквизита: полный
   `Settings.QueryText` динамического списка, EAV-свойства, индекс колонок.
4. `get_form_item(element_name[, column_name])` — детали элемента UI; с `column_name` — дочерний
   элемент колонки.
5. `find_form_element` — найти элемент по имени или по пути к данным (`data_path`), когда
   неизвестно, на какой он форме.
6. `search_form_properties` — поиск элементов по **любому** свойству EAV
   (`property_path` + значение), а не только по `Visible`/`Enabled`.

По умолчанию свойства элементов **курируются** (`verbose=false`): скрыт служебный шум, локализация
схлопнута, профильные свойства идут первыми, а число скрытых строк указано в ответе. Полный дамп —
`verbose=true`, но он редко нужен.

## Роли и права {#roles}

- `find_role` / `list_roles` — найти роль или получить список.
- `get_role_rights` — центральный инструмент: grants, RLS, шаблоны ограничений. По умолчанию
  `merge=true` — эффективное состояние основной конфигурации вместе с расширениями; `merge=false`
  показывает один слой. Для `ПолныеПрава` и других тяжёлых ролей ответ по умолчанию сводный
  (`response_mode=summary`) — детали запрашивайте фильтрами `object_name` / `rights` / `rls`.
- `find_roles_for_object` — обратный вопрос: какие роли дают явный grant на объект. Если в
  конфигурации есть `ПолныеПрава`, в ответе будет отдельная пометка — не забывайте её учитывать,
  иначе вывод «доступ только у роли X» будет неверным.

## Схемы компоновки данных {#dcs}

`get_dcs_schema` — то же для СКД, что `get_form_structure` для формы: наборы данных с текстом
запроса и полями (роли «измерение» / «баланс» / «период»), параметры, вычисляемые и итоговые поля,
сводка вариантов настроек.

Важно: **СКД крепится не только к отчётам.** Тысячи схем висят на справочниках, документах и
регистрах — часто это встроенные правила отбора или выборки для BSL, а не вывод отчёта; смотрите
подсказку `has_query`. Без параметра `template` возвращается обзор всех схем объекта; полный
документ отдаётся, когда схема одна или шаблон указан явно.

## Особые виды объектов {#special}

- **Регламентные задания:** список — `list_objects(object_type="ScheduledJob")`; детали
  (`method_name`, `use`, расписание перезапусков) — `get_object_structure`. У процедур общего
  модуля, на которые ссылается задание, `get_module_procedures` ставит пометку «регл. задание».
- **Бизнес-процессы:** `get_object_structure` дополнительно отдаёт точки маршрута и переходы
  (полный граф со Split/Join и подписями веток условий).
- **Определяемые типы:** индексируются как обычные объекты; `get_object_structure` показывает
  состав типа, `find_referencing_objects` работает и по ним.
- **Константы:** реквизитов и собственных форм у константы нет — `get_object_structure` показывает
  тип хранимого значения (`types`) и модули; код лежит в `ValueManagerModule` (модуль менеджера
  значения), реже — в `ManagerModule`. Если тип ссылочный, константа видна в
  `find_referencing_objects` по объекту-цели.
- **Регистры:** код набора записей — это `module_type="RecordSetModule"` (`ObjectModule` у регистров
  не бывает); `ManagerModule` рядом — отдельный модуль.
- **Подписки на события:** отвечают на вопрос «что ещё срабатывает, когда я пишу этот объект» —
  логика, которой нет в модуле самого объекта и которую поиском по коду не найти. С двух сторон:
  от объекта — `find_referencing_objects(имя, relation_kinds=["event_subscription"])` вернёт
  подписки с событием и обработчиком; от подписки — `get_object_structure` покажет `event`,
  `handler` и список источников. Своего кода у подписки нет, обработчик всегда лежит в общем
  модуле, и в `get_module_procedures` такая процедура помечена «[подписка на событие]».
  Оговорка: подписка может быть оформлена на **вид целиком** («все документы») — такие источники
  показаны отдельным полем `source_kinds` и в обратный поиск по конкретному объекту не попадают,
  так что для инфраструктурных событий проверяйте и его.
- **Расширения:** `active_databases` показывает у расширения его назначение
  (`Customization` / `AddOn` / `Patch`), а объекты помечены принадлежностью
  (`Own` — свой, `Adopted` — заимствованный).

## Границы: чего сервер не делает {#limits}

- **Не читает данные информационной базы.** Остатки, документы, пользователи, сеансы — это
  data-mcp, не сюда.
- **Ничего не меняет.** Ни в конфигурации, ни в индексе. Пересборка индекса — операторская
  операция в Хабе / admin-tool.
- **Не проверяет синтаксис встроенного языка и не знает платформенного API.** Сигнатуры методов,
  синтаксис языка запросов — help-mcp (`get_syntax` / `search_syntax` / `get_query_syntax`).
- **Не видит того, чего нет в выгрузке.** Если объект добавили в конфигурацию после последней
  сборки индекса, здесь его не будет — сначала пересборка.
- Подписки на события в графе связей пока не участвуют (запланировано); функциональные опции — не
  в графе, а в отдельном `get_functional_options`.

## Грабли {#pitfalls}

- **Пустой ответ ≠ поломка.** Чаще всего это «в этом проекте такого нет» или слишком узкий фильтр.
  Проверьте `project_filter` по `active_databases`, прежде чем расширять поиск.
- **Устаревшая или собирающаяся база молча выпадает** из выдачи остальных инструментов. Если
  объект «пропал» — проверьте флаги в `active_databases`.
- **Усечение выдачи.** Широкие объекты и роли обрезаются, но всегда сообщают об этом
  (`is_truncated`, «показаны N из M»). Не делайте вывод по усечённому списку: сузьте фильтр или
  возьмите точечный инструмент (`find_attribute` вместо полного `get_object_structure`).
- **`search_code` по имени объекта — почти всегда ошибка.** Для связей есть
  `find_referencing_objects`, для типов — `get_object_structure`.
- **Расширения меняют картину прав.** Ответ `get_role_rights` с `merge=false` — это один слой, а
  не то, что реально действует.

## Карта инструментов {#tools}

- `guide` — эта справка; `section` открывает раздел, `section="all"` — весь текст.
- `set_context` — один раз задать `task_id` / `session_id` / `agent` / `model` для журнала вызовов; на результаты не влияет.
- `active_databases` — список проектов и баз, источник `project_filter` и `extension_filter`; обязательный первый шаг.
- `list_objects` — объекты конфигурации по виду (`Catalog`, `Document`, `ScheduledJob`, …).
- `find_object` — поиск объекта по неточному имени или синониму.
- `get_object_structure` — состав объекта: реквизиты с типами, измерения, ресурсы, ТЧ, формы, модули, команды, точки маршрута.
- `find_attribute` — точечный поиск реквизита по имени, когда объект большой.
- `get_functional_options` — какие функциональные опции управляют объектом или элементом формы.
- `find_referencing_objects` — обратный поиск: кто ссылается на объект (реквизиты, формы, подсистемы, роли).
- `search_code` — поиск фрагмента в тексте BSL-модулей, в `QueryText` форм и в запросах СКД.
- `get_module_procedures` — оглавление модуля: процедуры, экспортность, директивы компиляции.
- `get_procedure_code` — текст одной процедуры вместе с директивой.
- `get_module_code` — полный текст модуля, включая модули команд.
- `find_form` — поиск формы по объекту и/или имени формы.
- `find_form_element` — поиск элемента формы по имени или пути к данным.
- `get_form_structure` — обзор формы: реквизиты с типами, дерево элементов, команды.
- `get_form_attribute` — детали реквизита формы: `QueryText`, свойства EAV, индекс колонок.
- `get_form_item` — детали элемента UI формы, включая дочерние элементы колонок.
- `search_form_properties` — поиск элементов форм по любому свойству EAV и его значению.
- `list_roles` — список ролей проекта или базы.
- `find_role` — поиск роли по имени или синониму.
- `get_role_rights` — права роли: grants, RLS, тексты ограничений; сведение слоёв основной конфигурации и расширений.
- `find_roles_for_object` — какие роли дают явные права на объект.
- `get_dcs_schema` — схема компоновки данных объекта: наборы, запросы, поля, параметры, варианты.
